## Numbered findings

### 1. HIGH: Rocket.Chat still claims three separately merged PRs

- Rules: R-17, R-38.
- Evidence: index.html:314 labels the value 3 as "PRs Merged". The paragraph below and the Open Source section correctly say the originals were closed and consolidated into maintainer PR #39853. This also contradicts the owner's explicit correction.
- Proposed fix: change that metric to "Original PRs" and keep all three original links, their closed/consolidated status, and the maintainer PR. Do not remove the Experience entry.
- Why it matters: the most visible metric contradicts the actual contribution history.

### 2. HIGH: a fixed activity snapshot is presented as a rolling year

- Rules: R-17, R-38.
- Evidence: script.js:645 identifies the embedded period as October 20, 2025 through October 25, 2026; script.js:651 fixes its start date. index.html:520 and script.js:685 call the total "contributions in the last year". The script explicitly states the dataset is static. Competitive Programming says "Published profile figures" without a publication date, although REVIEW.md identifies those figures as an older snapshot.
- Proposed fix: label the calendar with its actual date range or snapshot end date, and date the competitive-programming figures using the existing review evidence. Do not invent newer totals or silently change the dataset.
- Why it matters: historical data reads as current activity.

### 3. HIGH: tablet layout compresses projects into unusable columns

- Rules: R-03, R-35.
- Evidence: at a 768px browser viewport, #projects-grid measured 275.2px wide, with two 121.6px columns. The Midnight Network preview measured 88px high but contained 198px of content. The screenshot visibly clips its code and wraps project descriptions into very short lines. Project action links extend beyond their individual card column. A zero page-overflow measurement did not mean the layout was usable.
- Proposed fix: keep a readable content column through tablet widths and switch to two project columns only when the cards have enough space. Let source-preview content reflow without clipping. Retain the existing project order.
- Why it matters: checking only phone and wide-desktop widths missed a broken intermediate layout.

### 4. HIGH: mobile controls and project links miss the touch-target minimum

- Rule: R-03.
- Evidence at 390px: theme button 28 x 28px; command button approximately 46.2 x 21.1px; persona tabs approximately 18.2px high; first project action link approximately 15.2px high; demo links approximately 19.8px high. The skill requires 44 x 44px targets. More builds already measured approximately 57.1px high and does not have this particular defect.
- Proposed fix: enlarge hit areas and spacing on the affected controls without inflating their visual treatment. The protected Thing toggle is outside this proposed change; any change to it would require a separate explicit exception from the owner.
- Why it matters: compact desktop controls are difficult to activate accurately on a phone.

### 5. HIGH: muted text fails dark-mode contrast

- Rules: R-25, R-34.
- Evidence: computed dark-mode colors for #gh-total-count, .pr-status, and .origin-label were rgb(113, 113, 122), or #71717a, at 10-11px. The installed contrast checker calculated 4.35:1 against #000000 and 4.12:1 against #09090b. Both fail the 4.5:1 requirement for normal text. Several custom selectors keep that same color in both themes.
- Proposed fix: use a consistent, measured dark-mode secondary-text color for these selectors and check actual backgrounds in both themes. Preserve the companion's protected styles.
- Why it matters: the small status and date labels become harder to read in the shipped dark theme.

### 6. MEDIUM: the Midnight Network preview does not demonstrate its distinguishing work

- Rules: R-14, R-31.
- Evidence: index.html:440 features the two-line excerpt "r.close()" and "up = code < 400". It is authentic source, but it explains neither interval checks, persisted history, nor incident transitions, the reasons this project is featured. The surrounding screenshot-sized panel gives those two lines disproportionate space.
- Proposed fix: use an actual project screenshot if one is available, or a compact, explicitly labeled explanation of check storage and incident transitions. Do not fabricate live monitoring output or introduce a play overlay.
- Why it matters: the preview looks technical without providing useful evidence of the project.

### 7. MEDIUM: Skills uses inaccurate symbols while project rows use real logos

- Rule: R-04.
- Evidence: the PostgreSQL skill at index.html:686 contains a question-mark-in-a-circle path, while project technology rows use the local PostgreSQL elephant logo. The skill labeled Git at index.html:696 uses the GitHub mark. The Node.js skill is a generic geometric mark, while the project card uses the official Node.js logo.
- Proposed fix: use the already available authentic assets consistently, or use plain skill names where an accurate asset is unavailable. Distinguish Git from GitHub.
- Why it matters: the same technology has different visual identities, and some icons represent a different thing.

### 8. LOW: project-detail navigation and metadata do not follow the displayed order

- Rules: R-05, R-31.
- Evidence: homepage order is GrindLens, Midnight Network, Open Chat, Discord Reporter. projects/grindlens.html:24 skips Midnight Network and links next to Open Chat. projects/midnight.html:22 links back to GrindLens, while older pages say "Next project". Some pages use project numbers and others categories; GrindLens has an Overview sidebar but lacks the Built with list present on other detail pages.
- Proposed fix: choose one detail-page navigation sequence matching the homepage, use consistent metadata conventions, and add GrindLens's already verified technology list. Keep every relative .html URL.
- Why it matters: the detail pages still feel like several revisions joined together.

### 9. LOW: the same descriptions and figures are repeated instead of layered

- Rules: R-05, R-16.
- Evidence: the GrindLens problem statement, features, and figures appear in Experience, its project card, and its detail page. Rocket.Chat and NSoC repeat detailed contribution summaries in both Experience and Open Source. The hero bio and bullets also repeat those destinations. These facts are useful, but each repetition adds length without new information.
- Proposed fix: keep every requested section and Experience entry, but give each a different job: short role summaries in Experience, product behavior and links on cards, and implementation/evidence on detail pages and in Open Source. Preserve the owner's casual, direct voice rather than replacing it with sterile labels.
- Why it matters: the portfolio reads as accumulated edits rather than one deliberate narrative.

### 10. LOW: action labels are ambiguous or inconsistent with their destination

- Rule: R-15.
- Evidence: the Experience "View All" link opens LinkedIn, not more experience on this page. Project links alternate between "Live", "Live demo", the domain name, and "Open live project" without a clear convention. Some pages repeat the project name in the eyebrow immediately above the same H1. The source links say GitHub on cards and Source code on detail pages.
- Proposed fix: use destination-specific wording such as "Experience on LinkedIn", a consistent short live/source/detail vocabulary, and remove redundant eyebrow text where it supplies no additional context.
- Why it matters: visitors should know what pressing a link will do.
